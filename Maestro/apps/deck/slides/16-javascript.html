Quando o YAML não basta: JavaScript

javascript nos flows
# expressão inline dentro do próprio YAML
- evalScript: "${output.email = 'qa' + Date.now() + '@t.com'}"
- tapOn: {id: "email_input"}
- inputText: "${output.email}"

# copiar da tela e validar com lógica
- copyTextFrom: {id: "codigo_pedido"}
- evalScript: "${output.ok = maestro.copiedText.length === 8}"
- assertTrue: "${output.ok}"
// scripts/gerar-cpf.js — arquivo .js de verdade
function gerarCPF() {
  const n = () => Math.floor(Math.random() * 9);
  return Array.from({length: 11}, n).join('');
}
output.cpf = gerarCPF();
console.log('CPF gerado: ' + output.cpf);

# no flow:
- runScript: ../scripts/gerar-cpf.js
- inputText: "${output.cpf}"
# objeto faker embutido: dado falso realista
- inputText: "${faker.person.fullName()}"
- inputText: "${faker.internet.email()}"

Motor e limites

Roda em GraalJS por padrão, com ECMAScript moderno. Rhino existe, mas é desencorajado.

É um sandbox: sem acesso ao sistema de arquivos e sem require de pacotes npm. Você não instala lodash nem axios ali dentro.

Por que o sandbox é proposital

Garante que o flow escrito na sua máquina se comporte igual na máquina do colega e na nuvem. Portabilidade acima de poder.

Cuidado: não é o JavaScript do seu app. É um script auxiliar do teste — ele não enxerga o estado do React nem os hooks.

Analogia

O YAML é a partitura. O JavaScript é a improvisação combinada em cima dela — permitida, útil, mas ninguém improvisa a sinfonia inteira.
