Ato 01 · contexto

Onde o Maestro entra na pirâmide de testes

clique em cada camada

poucos, lentos, caros

Testa o aplicativo inteiro, montado

Abre o app instalado no emulador e percorre a jornada real: login, carrinho, checkout. É o único nível que pega erro de integração entre telas, navegação, permissão do sistema e API real. É aqui que o Maestro vive.

Analogia: é o ensaio geral da peça, com figurino, luz e plateia.

médios

Testa uma tela ou um componente isolado

Renderiza o componente em memória, sem emulador. Rápido, mas o app não existe de verdade: navegação, APIs nativas e permissões estão todas mockadas.

Analogia: é o ensaio de uma cena só, sem cenário.

muitos, rápidos, baratos

Testa uma função pura

Entrada e saída, milissegundos por teste. Não sabe nada sobre botão, tela ou usuário.

Analogia: é afinar um instrumento sozinho, em casa.

Maestro não substitui Jest nem Testing Library. Ele ocupa o topo da pirâmide, onde os testes são poucos porém decisivos.

Ato 01 · a virada de chave

Três formas de olhar para o app

Analogia · o mecânico com o capô aberto

Ele mede a pressão de cada peça isoladamente. Sabe exatamente qual válvula falhou — mas nunca descobre se o carro é ruim de dirigir na chuva. Rápido e preciso, porém longe da experiência real.

Analogia · o carro com sensores de fábrica

O mecânico dirige, e o painel avisa "motor ocupado, espere". A sincronia é perfeita: nunca acelera antes da hora. O preço é que os sensores precisam ser instalados na fábrica — e cada modelo novo de motor exige um sensor novo.

Analogia · o motorista comum

Ele senta, olha o painel, vira a chave e dirige. Não sabe nada do motor — e é exatamente por isso que dirige qualquer carro: React Native, Flutter, Kotlin, Swift, tanto faz. É assim que o Maestro trabalha, no que a documentação chama de operar "à distância de um braço": ele pilota o dispositivo, não o app.

Ato 02 · a solução

Maestro, em uma frase

Um framework open source de automação de UI que percorre o seu app pela mesma camada de acessibilidade que um leitor de tela usa — descrito em arquivos YAML legíveis por qualquer pessoa da equipe.

Tolerância embutida

Assume que o celular é instável: se o elemento ainda não apareceu, ele tenta de novo antes de falhar.

Espera inteligente

Aguarda sozinho conteúdo de rede e fim de animação. Sem sleep() na mão.

Sintaxe declarativa

Você descreve o quê, não como. Um QA sem background em programação lê e escreve o teste.

Iteração instantânea

Não compila nada. Salvou o arquivo, o flow roda de novo no aparelho na hora.

Binário único

Um comando de instalação e acabou. Nenhum pacote npm entra no seu projeto React Native, nenhuma linha do seu app muda.

flows/login.yaml — um teste completo
appId: com.exemplo.maestro
---
- launchApp:
    clearState: true
- tapOn:
    id: "email_input"
- inputText: "ana@empresa.com"
- tapOn:
    id: "senha_input"
- inputText: "123456"
- tapOn: "Entrar"
- assertVisible: "Bem-vinda, Ana"

A árvore de acessibilidade é o segredo

Todo sistema operacional mantém uma árvore com o que está na tela: texto, rótulo, identificador, posição, se está habilitado. Ela existe para o TalkBack e o VoiceOver funcionarem. O Maestro lê essa árvore em vez de ler o seu código — por isso um teste só serve para Android e iOS, e para app nativo, React Native ou Flutter.

Efeito colateral bom: acessibilidade

Se o Maestro não acha o botão, muito provavelmente o leitor de tela também não acha. Escrever teste acaba virando um checklist involuntário de acessibilidade do app.

Analogia: o maestro não lê a cabeça dos músicos; ele lê a partitura que está na estante de todos.

Ato 03 · sintaxe

Anatomia de um flow

.maestro/flows/checkout.yaml
appId: com.exemplo.maestro
tags: [smoke, checkout]
env:
  PRODUTO: "Plano Anual"
---
- launchApp
- tapOn: "${PRODUTO}"
- assertVisible: "Resumo do pedido"
- tapOn:
    text: "Aplicar cupom"
    optional: true
- tapOn:
    id: "btn_pagar"
    label: "Confirmar o pagamento"
- assertVisible: "Compra aprovada"

appId — o endereço do app

É o package name no Android ou o bundle identifier no iOS. Sem ele o Maestro não sabe o que abrir. Em Expo Go se usa openLink no lugar.

tags — etiquetas de execução

Permitem rodar só um subconjunto: maestro test --include-tags smoke flows/. Clássico: no pull request roda só o smoke; de madrugada roda tudo.

env — variáveis

Interpoladas com ${VARIAVEL}. Podem vir do config.yaml, do próprio flow ou do terminal com -e SENHA=123 — é assim que segredo não vai para o Git.

--- — a linha divisória

Acima dela, configuração. Abaixo, a lista ordenada de comandos. É YAML puro: cada traço é um passo, executado de cima para baixo.

optional — o passo que pode faltar

Se o elemento não aparecer, o Maestro segue em frente em vez de reprovar o teste. Perfeito para banner de cookie, pop-up de avaliação e promoção que só aparece às vezes.

label — legibilidade do relatório

Troca o texto técnico por uma frase de negócio no log e no vídeo do teste. Quem lê o relatório vê "Confirmar o pagamento" em vez de "tapOn id=btn_pagar".

11:15 – 12:45 · Clique em cada etiqueta: a linha correspondente acende no código. Comece pelo --- para explicar a divisão cabeçalho/comandos, depois volte para o resto.

Dois destaques que valem ponto: optional (resolve o pop-up aleatório, dor real de quem testa app) e -e SENHA=123 (segredo fora do repositório).

A única "integração" que existe

O testID do React Native vira Resource ID no Android e accessibilityIdentifier no iOS. O Maestro lê esse valor pelo seletor id.

Dá para mirar pelo texto visível (tapOn: "Entrar"), mas isso quebra quando alguém traduz o app ou troca o rótulo. testID é a prática recomendada.

12:45 – 14:15 · Slide principal do seminário. Clique nos três elementos do celular: o JSX e o YAML acendem juntos. Deixe o clique respirar antes de falar.

A frase-chave: "a única coisa que eu mudo no meu app React Native é acrescentar testID nos componentes — e testID nem é do Maestro, é do próprio React Native". Isso responde diretamente a pergunta "qual o contato dela com RN em JS".

Comente também o caso do iOS: quando componentes ficam muito aninhados, o RN "engole" o toque, e a documentação recomenda accessible={false} no container externo e accessible={true} no interno.

Ato 03 · como achar um elemento

Seletores: as coordenadas do teste

seletores
# forma curta: só o texto visível
- tapOn: "Entrar"

# todo texto é REGEX por padrão
- tapOn:
    text: ".*Continuar.*"

# cuidado: escapar caracteres especiais
- assertVisible: "R\$ 199,90"
# o mais estável: id técnico
- tapOn:
    id: "btn_entrar"

# Android → Resource ID
# iOS     → accessibilityIdentifier
# React Native → testID

- assertVisible:
    id: "icone_carrinho"
# três botões "Comprar" na mesma tela?
# index começa em 0
- tapOn:
    id: "btn_comprar"
    index: 2          # o terceiro

# funciona, mas é frágil:
# mudou a ordem da lista, quebrou o teste.
# "o botão Excluir que está NA LINHA do Plano Anual"
- tapOn:
    text: "Excluir"
    rightOf:
      text: "Plano Anual"

# outros: above, below, leftOf,
# childOf, containsChild, containsDescendants
- assertVisible:
    id: "card_item"
    containsChild: "Aprovado"
# pelo estado do elemento
- assertVisible:
    id: "aceite_termos"
    checked: true

- assertVisible:
    text: "Finalizar"
    enabled: false   # deve estar desabilitado

# e por características físicas
- tapOn:
    width: 48
    height: 48
    tolerance: 6
# último recurso: coordenada na tela
- tapOn:
    point: "50%, 50%"   # centro

- tapOn:
    point: "100, 250"   # pixels absolutos

# útil para canvas, mapa, webview teimosa.
# ⚠ quebra em telas de tamanho diferente

A regra de bolso

1º tente id (testID) — sobrevive a tradução e a redesign.
2º use text quando o texto for parte do requisito ("Compra aprovada").
3º use relacionais em listas, onde todo item é parecido.
4º só use point em último caso.

Analogia: id é o CPF do elemento, text é o apelido dele, relacional é "o vizinho da casa amarela" e point é a coordenada de GPS — quanto mais para baixo, mais fácil de dar errado.

Detalhe que derruba teste

Os seletores text e id são interpretados como expressão regular. Cifrão, colchete e ponto precisam de barra invertida.

14:15 – 15:30 · Não leia as seis abas. Mostre text, id, relacionais com calma e cite as outras rapidamente.

O exemplo relacional é o que mais impressiona: "o botão Excluir que está à direita do Plano Anual". Esse é um problema clássico de lista que em outras ferramentas vira XPath ilegível.

Tolerância embutida

A documentação usa a expressão "abraçar a instabilidade": o celular é instável, então a ferramenta assume isso e reexecuta a busca em vez de reprovar no primeiro erro.

Espera por condição, não por relógio

Trocar "espere 5 segundos" por "espere até aparecer" deixa o teste ao mesmo tempo mais rápido (não dorme à toa) e mais estável (não desiste cedo demais).

Analogia

Dizer "espere 3 segundos" é combinar de encontrar alguém às 15h em ponto e ir embora às 15h01. Dizer "espere até aparecer" é ligar para a pessoa e esperar ela chegar. O segundo combinado quase nunca dá errado.

Motor e limites

Roda em GraalJS por padrão, com ECMAScript moderno. Rhino existe, mas é desencorajado.

É um sandbox: sem acesso ao sistema de arquivos e sem require de pacotes npm. Você não instala lodash nem axios ali dentro.

Por que o sandbox é proposital

Garante que o flow escrito na sua máquina se comporte igual na máquina do colega e na nuvem. Portabilidade acima de poder.

Cuidado: não é o JavaScript do seu app. É um script auxiliar do teste — ele não enxerga o estado do React nem os hooks.

Analogia

O YAML é a partitura. O JavaScript é a improvisação combinada em cima dela — permitida, útil, mas ninguém improvisa a sinfonia inteira.

Ato 04 · honestidade técnica

O que o Maestro não faz bem

Ele testa o app inteiro, nunca a peça

Não existe "rodar só essa função" nem medir cobertura de código. Se o cálculo do frete estiver errado, o Maestro só avisa que o valor na tela ficou diferente do esperado — não aponta a linha.

Como conviver: Jest embaixo, Maestro em cima. São complementares, não concorrentes.

Acentuação e emoji quebram no Android

É uma limitação conhecida e documentada: no Android o comando de digitação só suporta caracteres ASCII. Para um app brasileiro, digitar "João" num campo de nome é um problema real.

Como conviver: use dados de teste sem acento, ou preencha o campo via clipboard (setClipboard + pasteText).

Conteúdo dentro de WebView nem sempre aparece

A árvore de acessibilidade nativa às vezes não expõe o que está renderizado dentro de uma WebView — e o Maestro simplesmente não enxerga o botão.

Como conviver: no Android, declarar androidWebViewHierarchy: devtools no topo do flow faz o Maestro inspecionar a página pelo Chrome DevTools. Fluxo híbrido pesado ainda é território de ferramenta web.

Ele espera bem, mas no escuro

O Maestro não sabe o que a thread JavaScript do React Native está fazendo. Ele observa a tela, espera assentar e tenta de novo. O Detox, por ser caixa-cinza, sabe quando o app terminou de trabalhar.

Consequência: em apps com animação longa ou polling constante, ainda pode sobrar algum caso raro de instabilidade. Aí você paga com extendedWaitUntil.

Não é 100% "zero setup"

O CLI roda na JVM: versões de Java muito novas ou muito antigas dão problema — a recomendação oficial é Java 17 ou 21. Antes de cada execução ele instala um app-driver no aparelho, e dispositivos corporativos travados (MDM, fintech, POS) podem bloquear essa instalação. Nesses casos, não há solução: é usar outro aparelho.

E iOS continua exigindo macOS com Xcode.

Detalhes chatos do iOS

O hideKeyboard é instável porque o iOS não oferece API nativa para esconder o teclado — o Maestro simula um gesto. E listas com paginação (UITableView) podem se comportar de forma estranha por um bug do próprio XCTest, que o Maestro usa por baixo.

Como conviver: tocar numa área neutra da tela no lugar de esconder o teclado.

Local é grátis; paralelo, não

CLI e Studio são open source. Rodar centenas de flows em paralelo, em vários modelos de aparelho, é serviço pago — com limite recomendado de cerca de 20 minutos por execução.

Os comandos com IA (assertWithAI) também dependem de chave de API e, por natureza, não são determinísticos.

21:00 – 22:30 · Este slide vale muito ponto. Clique em pelo menos quatro itens — sugestão: não substitui unitário, ASCII no Android, sincronização por heurística e escala tem preço.

Postura: nenhuma dessas limitações é fatal, e quase todas têm contorno documentado. Apresentar os limites com naturalidade mostra que você estudou a ferramenta de verdade, não só a página inicial.
