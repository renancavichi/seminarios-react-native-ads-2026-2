Ato 03 · como achar um elemento

Seletores: as coordenadas do teste

seletores
# forma curta: só o texto visível
- tapOn: "Entrar"

# todo texto é REGEX por padrão
- tapOn:
    text: ".*Continuar.*"

# cuidado: escapar caracteres especiais
- assertVisible: "R\$ 199,90"
# o mais estável: id técnico
- tapOn:
    id: "btn_entrar"

# Android → Resource ID
# iOS     → accessibilityIdentifier
# React Native → testID

- assertVisible:
    id: "icone_carrinho"
# três botões "Comprar" na mesma tela?
# index começa em 0
- tapOn:
    id: "btn_comprar"
    index: 2          # o terceiro

# funciona, mas é frágil:
# mudou a ordem da lista, quebrou o teste.
# "o botão Excluir que está NA LINHA do Plano Anual"
- tapOn:
    text: "Excluir"
    rightOf:
      text: "Plano Anual"

# outros: above, below, leftOf,
# childOf, containsChild, containsDescendants
- assertVisible:
    id: "card_item"
    containsChild: "Aprovado"
# pelo estado do elemento
- assertVisible:
    id: "aceite_termos"
    checked: true

- assertVisible:
    text: "Finalizar"
    enabled: false   # deve estar desabilitado

# e por características físicas
- tapOn:
    width: 48
    height: 48
    tolerance: 6
# último recurso: coordenada na tela
- tapOn:
    point: "50%, 50%"   # centro

- tapOn:
    point: "100, 250"   # pixels absolutos

# útil para canvas, mapa, webview teimosa.
# ⚠ quebra em telas de tamanho diferente

A regra de bolso

1º tente id (testID) — sobrevive a tradução e a redesign.
2º use text quando o texto for parte do requisito ("Compra aprovada").
3º use relacionais em listas, onde todo item é parecido.
4º só use point em último caso.

Analogia: id é o CPF do elemento, text é o apelido dele, relacional é "o vizinho da casa amarela" e point é a coordenada de GPS — quanto mais para baixo, mais fácil de dar errado.

Detalhe que derruba teste

Os seletores text e id são interpretados como expressão regular. Cifrão, colchete e ponto precisam de barra invertida.
